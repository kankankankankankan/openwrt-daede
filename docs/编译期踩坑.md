# 编译期踩过的坑（每条都是实际卡住过的）

这个文件记录 build.sh 里那些「不加就会挂」的设置，以及为什么。
新增踩坑时追加一条，格式：现象 → 原因 → 处理。

---

## 1. GNU tar 拒绝以 root 运行

**现象** `make` 在第一个 host 工具就停：
```
configure: error: you should not run configure as root
       (set FORCE_UNSAFE_CONFIGURE=1 in environment to bypass this check)
```
连锁反应：`staging_dir/host/bin/sed` 编不出来 → `package/utils/lua [host]` 挂
→ 所有 Go 包跟着挂。**表现和「内存不够」一模一样。**

**原因** tar 5.x 的 configure 有 root 检查，OpenWrt 官方流程不在 root 下跑。

**处理** `cmd_build` / `cmd_pkg` / `cmd_fetch` 三处都 `export FORCE_UNSAFE_CONFIGURE=1`。
漏一处就复发 —— 之前就因为漏了 `cmd_fetch` 白排查半天。

## 2. git-proto 包的 tar 不是字节确定的

**现象**
```
Hash of the local file mihomo-meta-1.19.31.tar.gz does not match
  file: 74463f34...  requested: 2337ee0d...
```

**原因** `PKG_SOURCE_PROTO:=git` 的包，`PKG_MIRROR_HASH` 指向 OpenWrt 镜像上的
预构建 tar。如果 `dl/` 里存在一个**同名但内容不同**的旧文件（上次 git 现场打包
留下的），make 会反复用它，永远对不上。

**处理** `rm -f dl/<该文件>` 后 `make <路径>/download` 重新走镜像。
实测这样能拿到和 `PKG_MIRROR_HASH` 完全一致的文件。

**诊断命令**
```sh
sha256sum dl/<文件>                       # 实际的
grep MIRROR_HASH feeds/.../Makefile       # 期望的
```

## 3. 什么时候多线程、什么时候单线程

### 脚本固定这么跑（三级降级，照抄 CI）

```bash
make -j$JOBS   →  失败  →  make -j1  →  失败  →  make -j1 V=s
```

| 级别 | 参数 | 用途 |
|---|---|---|
| 1 | `-j8`（`JOBS` 决定） | 正常编，大部分时间在这级 |
| 2 | `-j1` | 并行失败时降级，串行不会互相踩 |
| 3 | `-j1 V=s` | 还失败就出详细日志 |

**「失败」不是重试，是降配置。** 已编好的包靠 `.built` 跳过，
第 2、3 级不会从头再来。

### 各阶段用几个线程

| 阶段 | 线程 | 原因 |
|---|---|---|
| `fetch` 的 `make download` | **`-j8`** | 纯下载，IO 密集，并行最划算 |
| `fetch` 的逐包 download | **`-j8`** | 同上 |
| `build` 第 1 级 | **`-j$JOBS`** | 编译 |
| `build` 第 2/3 级 | **`-j1`** | 降级 |
| `pkg` 默认 | **`-j$JOBS`** | 单包编译 |
| `pkg -v` | **`-j1 V=s`** | 排错，必须串行 |

**`pkg -v` 永远单线程** —— 并行时 make 只报「failed to build」，
真话被吞掉，必须 `-j1 V=s` 才看得见。

### 实测：多线程能到哪

```
.built  183 → 197 → 213 → 237 → 243 → 246 → 256
```

**每一轮都在推进，没有卡死。** 因为重跑时上一轮编好的包已经有 `.built`，
`make` 直接跳过。

所以看到「又降级了」不用慌，查一下 `.built` 数量：

```sh
find /work/immortalwrt/build_dir -maxdepth 3 -name .built | wc -l
```

数字在涨就是在收敛。**三遍还失败才是真问题**（那时候看第 3 级的 `V=s` 日志）。

### 想一次跑完

把 `JOBS` 调到 4 以下，慢但一轮到底。实测 `JOBS=8` 时
`mihomo-meta` 单包就要 13 分钟，一轮里必然有包超时。

| JOBS | 内存/线程（16G） | 备注 |
|---|---|---|
| 4 | 4G | 最稳，几乎一轮到底 |
| 8 | 2G | 本次实测，会降级但收敛 |
| 12 | 1.3G | 靠 swap 撑 |
| 16 | 1G | 大概率 OOM |

### 为什么 Go 包这么慢

| 包 | 耗时 |
|---|---|
| `mihomo-meta` | 787 秒 |
| `tailscale` | 585 秒 |
| `dae` / `daed` | 十几分钟 |

`go build` 要解依赖 + 编译 + 链接，三个 Go 包同时跑会抢 modcache。
`-j8` 时 9 个 Go 包并发，容易触发「no such file or directory」——
这也是第 2 级降级存在的意义。

## 4. 预下载必须走「逐包 download」

**现象** `make download` 跑完只有 438M，编译时还在下 583M 的
`linux-firmware`、142M 的内核、91M 的 gcc。

**原因** `include/toplevel.mk:199` 的
`DOWNLOAD_DIRS = tools/download toolchain/download package/download target/download`
只遍历 `.config` 里 `CONFIG_PACKAGE_*=y` 的包，**间接依赖下不到**。
内核、工具链源码是 dae→BPF 头→内核 这条链拉进来的。

**处理** `fetch` 第 13 步对所有带 `PKG_SOURCE` 的 Makefile 逐个调
`<路径>/download`，把依赖图走一遍（只下载不编译）。141 个包，约 3-5 分钟。

## 5. `grep -c` 没匹配时输出两行

**现象**
```
build.sh: line 492: 0
1: syntax error in expression (error token is "1")
```

**原因** `grep -c` 无匹配时**既输出 `0` 又退出码 1**，
所以 `x=$(grep -c ... || echo 1)` 得到 `"0\n1"` 两行，塞进 `$(( ))` 就崩。
`.config` 被清过还没重建时正好零匹配。

**处理** 只能 `|| true` + `${var:-0}`，不能用 `|| echo`。**共 4 处。**

## 6. 三个子命令的边界

| | 干什么 | 不干什么 |
|---|---|---|
| `fetch` | clone / feeds / `make download` | **不编译**（编了就会在这一步报编译错） |
| `offline` | 检查依赖齐不齐 | 不改任何东西 |
| `build` | `make`，三级降级 | 不下载 |

之前把 `tools/compile`、`toolchain/install`、内核 configure、bpf-headers、
9 个 Go 包预热全塞进 `fetch`，结果「只是预下载」却报了一串编译错。
**fetch 必须是纯下载。**

## 7. 降级机制（照抄 CI）

```bash
make -j$JOBS  ||  make -j1  ||  make -j1 V=s
```

第 1 级并行快；并行失败（解包冲突之类）降到单线程，串行不会冲突；
还不行才开 `V=s` 出真话。**失败是降配置，不是重试同样配置。**

已编好的包靠 `.built` 跳过，所以第 2、3 级不会从头再来。

---

## 8. 不要在 build_dir 里乱删

`build_dir` 里的 `.built` 是断点续编的依据。删了会重编。

更严重的是删 `staging_dir/*` —— 那是 make 装出来的**产物**，不是缓存。
删掉之后 make 认为「已装过」（stamp 还在），但 install 阶段找不到文件，
报 `cp: cannot stat .../libgcc_s.so.*`。

**只删 `build_dir/target-*/<包名>-*` 这类明确的单包目录，其余别动。**

## 9. 目标名的三种形态

| 形态 | 例子 | 何时用 |
|---|---|---|
| `package/feeds/<x>/<y>/compile` | `package/feeds/packages/dae/compile` | feed 包（**唯一正确形式**） |
| `package/<x>/<y>/download` | `package/kernel/bpf-headers/download` | 只下源 |
| `tools/<x>/compile` | `tools/tar/compile` | host 工具 |

去掉 `package/` 前缀拼成 `feeds/packages/dae/compile` 会报
`No rule to make target` —— 但这个错会掩盖真正的问题。

**判断包在哪**（`package/feeds/` 下是软链，且可能是断链）：
```sh
ls -l package/feeds/packages/<名>          # 软链指向哪
ls package/feeds/packages/<名>/Makefile    # 能不能读到
```

## 10. `make download` 也要 FORCE_UNSAFE_CONFIGURE

`make download` 内部会 `tools/flock/compile`、`tools/zstd`，
它们也是 configure 脚本，同样拒绝 root。`fetch` 里必须导出这个变量。

## 11. 多仓库更新边界

本地项目分为源码、软件源和固件编译三层：

| 层级 | 仓库 | 更新方式 |
|---|---|---|
| 插件源码 | `openwrt-daede` | `dae`、`daed`、`vmlinux-btf` 每两天检查上游；会员 LuCI 和同步脚本保留本地版本 |
| 固件软件源 | `ImmortalWrt-Packages` | 通过 `openwrt-daede` 目录提供固件编译使用的包 |
| 固件构建 | `ImmortalWrt-Actions` | 更新软件源后重新编译并在 Release 中记录 Packages 提交 |

`.github/workflows/upstream-sync.yml` 只同步上游核心目录，不覆盖 `luci-app-daede`。上游 LuCI 改动需要逐项检查，确认不影响会员界面、会员同步脚本和定时任务后再合并。

## 12. BTF 构建依赖

启用 `CONFIG_KERNEL_DEBUG_INFO_BTF=y` 或 `vmlinux-btf` 时，编译机需要 `pahole`。Ubuntu Actions 环境安装 `dwarves`：

```sh
sudo apt-get install dwarves
command -v pahole
pahole --version
```

缺少 `pahole` 会导致 `vmlinux-btf` 构建失败，随后 dae 或 daed 运行时可能找不到内核 BTF。
